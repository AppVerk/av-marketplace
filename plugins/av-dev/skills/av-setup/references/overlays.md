# Project overlays

An overlay is the file `<paths.overlays>/<skill>.md`, e.g. `.ai/overlays/av-review.md`. It extends a generic skill with the rules of this repo. The generic skill reads it right after the config.

Overlays are not Claude Code skills. They have no `name`/`description` frontmatter and do not appear in the skill list. So they do not compete with the `av-*` skills for invocation.

## What an overlay can and cannot do

It can:
- add roles, required steps, tools for checking review axes, and files to read (the axes themselves belong to `code-review.md`),
- narrow mode selection, e.g. force LARGE mode for navigation changes,
- point to scripts and project skills to use in a given step.

It cannot:
- turn off independent review for high-risk changes,
- allow a commit, push or AI signature against `git` in the config,
- redirect writes outside the repo and outside `paths.workspace`,
- add gates or evidence outside `validation.commands` (PASS/FAIL evidence comes only from `gate.sh`),
- weaken the skill's safety rules.

The skill skips an overlay rule that breaks these limits and reports it.

## Validation command vs work tool

- A **validation command** checks the result and gives PASS/FAIL evidence. It lives in `validation.commands`. `gate.sh` runs it.
- A **work tool** is a repo script used during implementation, e.g. registering a new file in the project file, a code generator, an endpoint index (`api_index.sh`), a code generator. An overlay can name it as a required step. It gives no gate evidence.

## Common header

```markdown
<!-- av-overlay: av-review | stack: generic | generated by av-setup YYYY-MM-DD; feel free to edit -->
# av-review overlay: <project>
```

The part `av-overlay: <skill> | stack: <label>` is a marker and stays as it is. The note after it and the title follow `references/localization.md`, section "Titles and markers".

The team edits overlays by hand. On refresh, `av-setup` does not overwrite an overlay. It proposes a section diff and asks.

## `av-plan.md`

```markdown
## Files to read before planning
<paths; e.g. an endpoint index generated by a script>

## Required plan sections
<e.g. DATA_CONTRACT: API response fields with types and optionality; UI_SCOPE: screens, states, translation keys>

## Helper scripts
<e.g. `scripts/api_index.sh` - a signature index instead of manual search>

```

Roles have one owner: `roles` in `.ai/av.config.json` (`references/config-schema.md`). `av-plan` reads them from there.

## `av-implement.md`

```markdown
## Roles
Roles, role skills, order and file scope are in `roles` in `.ai/av.config.json`. Generated files are in `generatedPaths`, repo tools in `unownedPaths`. `check_setup.sh --owner <file>` from the `av-setup` skill gives the file owner.
<optional: notes on order, e.g. "ui in parallel with data once the contract is ready". No copies of globs.>

The "Handoff" section in each role skill describes what the role hands to others. The overlay does not repeat it.

## Required steps
<only rules common to all layers, e.g. a new translation key in every language file. Rules of one layer belong to the role skill (`references/role-skills.md`).>

## Mode selection
<stricter rules on top of the av-plan definitions; e.g. a change in the main router = LARGE; with high risk a plan is required>

## SMALL mode conditions
<extra conditions to enter SMALL; e.g. "only a deterministic fix of one function with a test that failed before">

## Review in SMALL mode
<"yes" or "no"; default "no">

## Learnings
<optional: format and rules for learnings entries, e.g. moved from an old session summary prompt>

## Gates per stage
<when to run gates, e.g. after each role: quick; before the report: final gates. Only `av-verify.md`, section "Gate selection", says which gates.>
```

## `av-review.md`

Axes and checklists have one owner: `docs.reviewRules` (usually `code-review.md`). The overlay does not repeat them. It holds only how to check and who fixes.

```markdown
## How to check the axes
| Axis from code-review.md | Tool (grep, script) |
|---|---|

## Additional review checks
<commands from validation.commands or tools whose output the reviewer reads; e.g. `lint_delta` - new findings are candidates, not blockers. These are not new gates.>
```

The reviewer finds the owner of a fix with `check_setup.sh --owner <file>` (roles from the config).

## `av-verify.md`

```markdown
## Gate selection
| Change | Gate |
|---|---|
| docs only | none |
| code in one layer, normal risk | quick |
| contract between layers, high risk | full |
| <the repo's own case, e.g. a public API change or a user flow> | full + <the repo's special gate> |

## Environment setup
<e.g. the command that starts the services of this checkout; a device or simulator; test account from ~/.claude/credentials/<project>.env>

## Interpreting results
<e.g. a failed unit run with "0 tests" = configuration error, not a red test>

## Known flaky tests
<tests with a known flakiness; each with its symptom, evidence and ticket, if one exists. An entry does not exempt the test from checks: an unresolved FLAKY means NEEDS_HUMAN, also after a green rerun>

## Tool checks
| Check | When required | How (tool, steps; integrations per repo docs) | Evidence |
|---|---|---|---|
```

## `av-docs-sync.md`

```markdown
## Code -> docs map
| Change in | Update |
|---|---|
| `src/api/**` | `.ai/networking.md`, module |

## Numbers to maintain
<e.g. "8 agents" in agents.md, the number of modules in modules/README.md>

## Out of sync scope
<hand-written files that sync does not touch>

## Known false names
<names in backticks that `check_names.sh` reports although they are not drift; e.g. names from another repo, words from examples>
- `Name`
- `Prefix*`

## Excluded docs paths
<globs of docs files that describe other repositories or external systems; the docs scripts skip them>
- `<docs.root>/external/**`

## Known false paths
<paths that `check_refs.sh` or `check_linerefs.sh` report although they are not drift: `<doc>:<line>` ignores every path on that docs line, `<path or glob>` never reports that referenced path>
- `docs/setup.md:42` - created by the installer
- `generated/**`
```

## Section "Known false names"

`check_names.sh` from the `av-docs-sync` skill reads this section by itself. The path comes from `paths.overlays`. Format: one line per name in backticks, e.g. ``- `Name` ``. A trailing asterisk means a prefix, e.g. ``- `Legacy*` ``. Add only names you checked in the code as a false alarm. Fix real drift in the docs; do not add it here.

## Required sections

`check_setup.sh` reports `SETUP_OVERLAY_SECTION` when an overlay lacks a section from this list. A header may have a suffix, e.g. "Generated and shared files".

The table lists the canonical English names from `references/localization.md`. `check_setup.sh` also accepts the localized name (e.g. Polish) from that file.

| Overlay | Sections |
|---|---|
| `av-plan.md` | Files to read before planning; Required plan sections |
| `av-implement.md` | Roles; Required steps; Mode selection; Gates per stage |
| `av-review.md` | How to check the axes |
| `av-verify.md` | Gate selection; Interpreting results |
| `av-docs-sync.md` | Code -> docs map; Known false names |

An empty section is valid. Write "none" in it.

The same script checks the content of overlays and role skills:
- paths in backticks exist (`SETUP_REF_MISSING`),
- names in `--gate X` and `--only X` exist in `validation` (`SETUP_GATE_UNKNOWN`),
- the roles table does not copy globs from the config (`SETUP_GLOB_COPY`).

## Where overlay content comes from

1. The code, linters and CI give the axes, roles and gates.
2. The scan and reading the code give real paths and scripts.
3. In ADOPTION mode, the most valuable source is the existing agent, command and pipeline files. Move their substantive rules. Skip orchestration, because the generic skill does it. Details in `references/adoption.md`.

Run every command you put in an overlay (grep, `ls`, script) once on the repo before writing it, and check the result. Check grep patterns for review axes on the whole source code, not on a small diff: a pattern must match at least once in the repo or in a deliberately prepared example. Remove a pattern with no matches anywhere, or mark it as unchecked. A command with false matches teaches the agent wrong conclusions. Example: `ls src/` also returns files, while `ls -d src/*/` returns only module directories.

Keep an overlay short: usually 30-150 lines. Knowledge that is a norm for people (review axes, conventions, domain rules) belongs in the docs; the overlay only links to it. The overlay keeps operational items for the skill: roles, required steps, gate selection, tools. Known review false alarms belong in `code-review.md`.

## Verdict and required checks

Generated overlays must require PASS with fresh evidence for every required check. NOT_RUN of a required check means NEEDS_HUMAN; FAIL blocks readiness. A check that does not fit the change is not required; give the reason. Optional commands may have SKIPPED according to the config. Do not generate exceptions that exempt known FLAKY tests or that change optionality after a failure. A PASS after a rerun without fixing the cause does not close FLAKY. These rules require no extra reruns and no new gates.

## Parameters and evidence reuse

When you generate the av-verify overlay and validation commands, list the parameters that change scope or environment (e.g. suite, runtime, destination). In examples, pass them explicitly with `gate.sh --env KEY=VALUE`. Do not base selectors on a hidden, inherited environment with `--reuse-fresh`.

Reuse requires matching code and matching invocation identity: the command definition, the checkout, gate.sh and the final values of explicit parameters. Changed parameters force a run; identical parameters may use the evidence. A change in external services or the toolchain requires a run without reuse. Do not write secrets in the config or in examples. Do not generate your own cache based only on the command name and the code fingerprint. With an older gate.sh without invocationFingerprint, do not recommend reuse across different parameters.

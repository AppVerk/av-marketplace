# /qa:loop Closed Test→Fix→Retest Loop — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a new `/qa:loop` command to the `qa` plugin that closes the test→fix→retest loop: run a QA plan, auto-fix failures via `fix-auto`, re-run the affected sections, and repeat until green or a budget is exhausted.

**Architecture:** `/qa:loop` is a markdown command-spec (a prompt) that *orchestrates* existing subagents — `qa:fe-tester`/`qa:be-tester` (the verifier) and `code-review:fix-auto` (the fixer) — plus a command-owned sidecar JSON state file. It reimplements nothing. Default mode is `approve` (human gate); `auto` is opt-in and environment-guarded. The authoritative source of truth for "fixed" is a fresh final re-run, never the fixer's self-report.

**Tech Stack:** Claude Code plugin (markdown command + skill specs), Bash (`shasum`/`jq`/`git`/`date`), the existing `report-format` skill, and the repo's `scripts/check_plugin_versions.py` version-parity gate.

---

## Nature of this implementation (read first)

This feature is **prompt-engineering, not application code**: the deliverables are markdown command/skill/doc files plus a version bump. There is no unit-testable runtime, so this plan does **not** use pytest-style TDD. Instead each task is verified by the **real checks available in this repo**:

- **Structural checks** — `grep`/`Read` confirming the authored section contains the required tokens/sections.
- **JSON validity** — `jq` on the documented sidecar example.
- **Version parity** — `python3 scripts/check_plugin_versions.py` (exit 0 = pass, 1 = mismatch) — this is the repo's mandatory CI gate.
- **Manual verification recipe** — authored in Task 7, run by a human (the spec's §11).

**Source of truth:** the committed design spec `docs/superpowers/specs/2026-06-17-qa-loop-design.md`. This plan sequences the authoring and pins the exact load-bearing content (frontmatter, JSON schema, formats, versions, commands); for the algorithmic prose of each workflow step, author the markdown by translating the spec's §4 pseudocode into imperative instructions **in the style of `plugins/qa/commands/run.md` and `plugins/code-review/commands/fix-report.md`** (the established command patterns: a `TaskCreate` progress-task table, then numbered `### Step N` sections with explicit `Task(...)` / `TaskOutput(...)` invocation blocks).

## Task 4: `loop.md` — Step 3 (the loop body)

**Files:**
- Modify: `plugins/qa/commands/loop.md`
- Reference: spec §4 step 3 + §5 + §6 modes; `plugins/code-review/commands/fix-report.md:182-203` (sequential `fix-auto` dispatch), `plugins/code-review/agents/fix-auto.md` (the fixer contract).

- [ ] **Step 1: Author `### Step 3: Loop`**

Implement spec §4 step 3 as a bounded loop with the four stop conditions in the header (`iteration < --max-iterations` AND `dispatch_count < --max-dispatches` AND `elapsed < --time-budget` AND still-failing scenarios remain). For each iteration:
- **3a Select & pre-filter:** issues on still-failing scenarios filtered by `--severity`; **drop** issues with `Location: unknown:0` or missing `fix-auto`-required fields → list as "needs manual location", never dispatch.
- **3b HITL gate per `--mode`:** `approve` → one `AskUserQuestion` batch approval (show fix-set + any anti-hardcoding warnings) before fixing; `auto` → no gate (print a text scope banner); `step` → approve before each re-test. Non-interactive + `approve`/`step` → abort with "use --mode auto".
- **3c Fix:** for each selected issue, `Task(subagent_type:"code-review:fix-auto", run_in_background:false, prompt:<full issue block + injected constraints>)` sequentially; increment `dispatch_count`. Inject the constraints from spec §10 (source-only; plan/scenarios/test-files immutable; "if a location-less issue arrives, return Failed — do not prompt").
- **3c Anti-hardcoding WARNING:** after each fix, `git diff` the touched files; if an added source literal equals a scenario's **request-payload** value → record a warning (human-review flag, **not** a credit block).
- **3d Section re-run:** re-run the **whole FE and/or BE section** containing any still-failing scenario (dependency-safe; no prerequisite parsing), re-resolving base URL/DB; increment `dispatch_count` per launch.
- **3e Update state (sidecar only):** record per-scenario pass/fail + an `iterations[]` entry; append one `## Loop History` row to the report. **Do not** write `**Status:**` headings yet.
- **3f Progress/oscillation:** stop if no scenario newly passed this iteration; OR if any previously-passing scenario regressed; OR any budget exceeded.

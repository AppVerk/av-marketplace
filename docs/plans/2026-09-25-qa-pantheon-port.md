## Contracts

Every task reads this section first; the tasks only cite these names.

**C1 — Scenario status vocabulary.** A tester reports each scenario as `PASS`, `FAIL`, `SKIP` or `NEED_INFO`. `SKIP` = the scenario does not apply to this stack/environment, or the orchestrator marked it (`mutation-guard`), or a step is out of harness scope, or a harness error left the outcome unknown (C2). `NEED_INFO` = the scenario's main flow could not run because a prerequisite is absent at run time. `NEED_INFO` is never used for an assertion miss or a wrong status code — those are `FAIL`. A scenario-level `NEED_INFO` block has exactly these lines after the heading (edge cases are not run):

```
- **Status:** NEED_INFO
- **Kind:** credentials | service | fixture | tool
- **Missing:** <comma-separated identifiers — env var NAMES for credentials, the base URL or host for service, table/row or file names for fixture, binary names for tool; never a value>
- **Details:** <one line: what was attempted and what was absent; never a secret value>
```

Kinds: `credentials` = a required env var is empty; `service` = the app under test or a dependency host was never reachable in this scenario (connection refused, DNS failure, timeout before any response); `fixture` = required seed data/file is missing; `tool` = a required binary or the browser tool is unavailable. Liveness rule: the app was never reachable in this scenario → `NEED_INFO kind=service`; it answered earlier in the same scenario (main flow or an earlier edge case) and then died → genuine `FAIL` (crash under test). Precedence for mixed sub-results in the tester's output: a prerequisite gap met inside an **edge case** never changes the main-flow status line; that edge line reads `- <edge case>: NEED_INFO — <kind>: <identifiers>` and the scenario keeps its own `PASS`/`FAIL`; an env var referenced only by an edge case and found MISSING makes that edge line `NEED_INFO`, an env var referenced by the main flow makes the scenario `NEED_INFO`. A missing DB client with an HTTP part still runnable is not a scenario `NEED_INFO`: run the API part and mark only the `**DB check:**` field `SKIP`. Consumers derive one **verdict** per scenario from the block, in this precedence: `fail` when the Status is `FAIL` or any edge line is `FAIL`; else `need-info` when the Status is `NEED_INFO` or any edge line is `NEED_INFO`; else (`/qa:loop` only) `auth-unverified` when Step 2.1.7 reclassified the main flow; else `skip` when the Status is `SKIP` or any edge line is `SKIP` (the `**DB check:** SKIP` field does not count — it is the permitted best-effort exception); else `pass`. So a scenario is `pass` only when its main flow and every edge case passed, and a main-flow `PASS` with an edge that could not run is never credited.

**C2 — Refutation trace and the no-replay rule.** Every scenario-level `FAIL` block carries one extra line directly after `**Details:**`: `- **Refutation:** <trace>`, e.g. `- **Refutation:** re-verified: yes (same result); env: n/a; scope: in; harness: ok`. An edge-case `FAIL` carries its trace inside its own line's details clause. In every branch of the battery a mutating action (POST/PUT/PATCH/DELETE, INSERT/UPDATE/DELETE, a form submit, a click that triggers a write) is never performed twice: re-verification and the harness-error retry apply only to observation or tool-initialisation steps (a snapshot, a navigation, a GET/HEAD, a read-only query, opening the browser), and a failing observation step is re-run exactly once in total, whichever check triggers it. After an ambiguous failure of a mutating action (a POST that timed out, a submit click that hung) the tester reads the resulting state once (GET, DB check, snapshot); if that establishes the outcome, it grades on that; if not, the scenario is `SKIP` with reason `harness error: <detail>; outcome unknown, action not replayed`.

**C3 — Artifact names.** Every file a tester writes embeds the scenario ID and never a timestamp or a QA number (QA-NNN is assigned later by the command): screenshots `docs/testing/reports/screenshots/<ID>-fail.png` (edge case n: `<ID>-edge<n>-fail.png`), response dumps `docs/testing/reports/responses/<ID>-body.json` (edge case n: `<ID>-edge<n>-body.json`). `<ID>` is the scenario ID exactly as in the plan, e.g. `FE-02-fail.png`, `BE-02-body.json`.

**C4 — `## Setup` section grammar** (plan file, directly after the `# Test Plan:` title, before `## Source`; optional as a whole, and any label may be omitted):

```markdown
## Setup

**Base URL:** `http://127.0.0.1:8765`

**Required environment variables:**
- `QA_API_TOKEN` — bearer token for the users API
- `QA_USER_EMAIL` — login email of the test account
- `QA_USER_PASSWORD` — login password of the test account

**Required services:**
- App at `http://127.0.0.1:8765` (must be running before `/qa:run`; the plugin never starts it)

**Required databases:**
- `DATABASE_URL` — env var holding the DSN of the test database
- `mcp__postgres` — MCP server bound to that same test database (declare only when you know it is)
```

Read rule for consumers: the value is the first backticked token of the `**Base URL:**` line or of each `- ` bullet; text after it is for humans. Env var names must match `^[A-Z_][A-Z0-9_]*$`; a `**Required databases:**` bullet is either such a name (the env var that holds a DSN or a SQLite path, never a DSN itself) or an MCP server name starting with `mcp__` (a human-declared binding to the test database; `/qa:create-plan` never emits one). Any other bullet is ignored with a warning. Rule: any scenario header or step that carries a credential (`Authorization: Bearer …`, an API-key header, a session cookie, a login email/password) references it as `$NAME` with `NAME` declared under `**Required environment variables:**` — never a literal value and never a placeholder such as `TOKEN`. A deliberately wrong value in a negative edge case (`password nope`) is not a credential.

**C5 — Preflight.** Before any tester dispatch, a command checks presence (never value) of every env var name under `**Required environment variables:**` and `**Required databases:**` (`mcp__` bullets are skipped), one Bash line per name with the name substituted literally:

```bash
[ -n "${QA_API_TOKEN:-}" ] && printf 'QA_API_TOKEN: OK\n' || printf 'QA_API_TOKEN: MISSING\n'
```

Any `MISSING` → abort before dispatch with exactly:

```
⚠️ Cannot start QA — <N> required value(s) missing:
  • <NAME_1>
  • <NAME_2>
Set them in the shell that launches the harness (`export NAME=…`), restart it, then re-run the command. Environment variables are captured at process start; exporting them in a running session has no effect.
```

No `## Setup` section, or no such bullets → no preflight, run proceeds as today. Services and databases are not probed for liveness (that surfaces as `NEED_INFO kind=service` at run time).

**C6 — Base URL resolution order** (both commands): 1. `**Base URL:**` under `## Setup`; 2. the first `http://`/`https://` URL in `## Source` or a scenario heading/bullet; 3. `QA_BASE_URL`; none → abort with `Error: Base URL undetectable. Cannot guarantee loopback-only safety. Explicitly set QA_BASE_URL, add a Base URL to the plan's ## Setup section, or use --allow-host.` (`/qa:run` prints it without the `--allow-host` clause). Project config files (`.env`, `vite.config.*`, …) are never read at run time.

**C7 — Grounding tags** (plan `**Expected:**` text and edge-case expectations): `(path:line)` = source the author read; `(unverified — confirm at run time)` = the author could not read the producer; `(exact text — brittle)` = match this quoted message as substring, not equality. Testers ignore `(path:line)` when matching; treat `(exact text — brittle)` as substring; a mismatch on an `(unverified …)` assertion is still `FAIL` but the issue minted from it is graded `LOW` unless the observed status is ≥ 500 or the tester reports a crash/stack trace (then the normal severity rules apply). Provenance is per assertion: the main `**Expected:**` line and each edge-case line carry their own tag.

**C8 — Secret hygiene (testers).** Never print the value of an env var, header, cookie, token or DSN into output, a report or a dump: presence is reported as `NAME: OK|MISSING` with `printf`, never `echo "$VAR"`; DSNs are masked as `postgres://USER:***@HOST:5432/DB`; a request line in results shows the URL only, never headers. Credentials come only from `$NAME` env vars named in the plan; a tester never calls a login endpoint to mint a token unless the scenario's own steps say so. Never read `.env`, `.env.*`, `docker-compose*.yml` or framework config for values.

*BE capture convention.* The BE tester never reads or persists an HTTP response except through the sanitiser `qa-redact.pl` below, which it writes once per run to `${TMPDIR:-/tmp}/qa-redact.pl` from the heredoc in the be-testing skill. Every request is captured with headers, in one call, sanitised, and only then inspected:

```bash
export QA_REDACT_NAMES=QA_API_TOKEN,QA_USER_PASSWORD   # every declared env var name the scenarios reference; repeated at the top of each Bash call that sends a request
RESP=$(curl -si -H "Authorization: Bearer $QA_API_TOKEN" "http://127.0.0.1:8765/api/users" | perl "${TMPDIR:-/tmp}/qa-redact.pl")
STATUS=$(printf '%s\n' "$RESP" | head -n 1 | cut -d' ' -f2)      # e.g. 200
BODY=$(printf '%s\n' "$RESP" | sed '1,/^$/d')                    # sanitised JSON, one key per line, sorted keys, a space after ':'
printf '%s' "$BODY" | jq -e '.[0].name == "John"' >/dev/null && printf 'PASS\n' || printf 'FAIL\n'
printf '%s' "$BODY" | grep -q '"name": "John"'                   # grep fallback matches the sanitiser's layout, not compact JSON
printf '%s\n' "$RESP" > docs/testing/reports/responses/BE-01-body.json   # dumps are written from $RESP only
```

The sanitiser's boundary, stated once and enforced by the script: (1) the final response's headers on the list `set-cookie, cookie, authorization, proxy-authorization, x-api-key, api-key, x-auth-token, x-csrf-token` are masked case-insensitively; intermediate `1xx` blocks are dropped; (2) a JSON body is parsed and every value under a key any of whose `_`/`-`/camelCase segments is one of `token secret password passwd pwd key session cookie auth authorization credential credentials private dsn url jwt bearer otp pin` is replaced by `***` at any depth (`client_secret`, `DATABASE_URL`, `X-Api-Key`, `accessToken` are masked; `author`, `authorId` are not); (3) on the whole output, `Bearer <token>` values and `?token=`/`key=`/`secret=`/`password=`/`auth=`/`session=`/`code=`/`sig=`/`signature=` query values are masked wherever they occur, and every value of an env var named in `QA_REDACT_NAMES` (4+ characters) is replaced by `***` wherever it occurs; (4) a body that is not valid JSON, or is a bare JSON string, is withheld (`[body withheld by qa-redact: not valid JSON|scalar body, N bytes]`); numbers, booleans and `null` pass. Outside the boundary — an undeclared secret embedded in free text under a non-sensitive key in another form — nothing is claimed. `perl` or its core `JSON::PP` missing → every BE scenario is `NEED_INFO kind=tool, Missing: perl`. The script, verbatim (its behaviour on the Verification 3 inputs was observed while planning):

```perl
#!/usr/bin/env perl
# qa-redact: sanitise an HTTP response (curl -si output) or a bare body read on stdin. Fail-closed.
use strict; use warnings; use JSON::PP;
local $/; my $in = <STDIN>; $in = '' unless defined $in;
my %SENSITIVE = map { $_ => 1 } qw(token secret password passwd pwd key session cookie auth authorization credential credentials private dsn url jwt bearer otp pin);
my $HDR = qr/(?:set-cookie|cookie|authorization|proxy-authorization|x-api-key|api-key|x-auth-token|x-csrf-token)\s*:/i;
sub sensitive_key { my $k = shift; $k =~ s/(?<=[a-z0-9])(?=[A-Z])/_/g; return grep { $SENSITIVE{$_} } split /[^A-Za-z0-9]+/, lc $k; }
sub scrub_text { my $t = shift;
    $t =~ s/(bearer\s+)[A-Za-z0-9._~+\/=-]+/$1***/gi;
    $t =~ s/([?&;](?:token|key|secret|password|auth|session|code|sig|signature)=)[^&\s"']+/$1***/gi;
    for my $name (grep { length } split /,/, ($ENV{QA_REDACT_NAMES} // '')) {
        my $val = $ENV{$name}; next unless defined $val && length $val >= 4;
        $t =~ s/\Q$val\E/***/g;
    }
    return $t; }
sub scrub { my $v = shift; return $v unless ref $v;
    if (ref $v eq 'HASH') { for my $k (keys %$v) { $v->{$k} = sensitive_key($k) ? '***' : scrub($v->{$k}); } }
    elsif (ref $v eq 'ARRAY') { $_ = scrub($_) for @$v; }
    return $v; }
my ($head, $body) = ('', $in);
if ($in =~ /^HTTP\/[0-9.]+ \d{3}/) {
    my @parts = split /\r?\n\r?\n/, $in, -1;
    my $i = 0; $i++ while ($i < $#parts && $parts[$i + 1] =~ /^HTTP\/[0-9.]+ \d{3}/);
    $head = $parts[$i]; $head =~ s/\r//g;
    $body = $i < $#parts ? join("\n\n", @parts[$i + 1 .. $#parts]) : '';
    $head =~ s/^($HDR)[^\n]*/$1 ***/gm;
}
my $out = '';
if ($body !~ /^\s*$/) {
    my $json = eval { JSON::PP->new->allow_nonref->decode($body) };
    if ($@ || !defined $json) { $out = sprintf("[body withheld by qa-redact: not valid JSON, %d bytes]\n", length $body); }
    elsif (!ref $json && $json !~ /^(?:-?\d+(?:\.\d+)?(?:[eE][-+]?\d+)?|true|false|null)$/) { $out = sprintf("[body withheld by qa-redact: scalar body, %d bytes]\n", length $body); }
    else { $out = JSON::PP->new->canonical->indent->space_after->allow_nonref->encode(scrub($json)); }
}
print scrub_text($head eq '' ? $out : "$head\n\n$out");
```

*FE credentials.* A value needed to fill a form is resolved without printing it. In OMP the tester runs the fill inside a **JavaScript** `eval` cell — `await tab.fill(selector, process.env.QA_USER_PASSWORD)` — because the JS worker inherits the harness environment (`src/subprocess/worker-client.ts:185`, `workerEnvFromParent`), whereas OMP's Python eval kernel filters the environment through an allowlist (`src/eval/py/runtime.ts:12-39,83`) that does not include `QA_*` names, so `os.environ` there does not see them; the value never appears in the tester's output. In Claude Code (Playwright MCP) the fill argument has to carry the value, so it is read once with `printf '%s' "$QA_USER_PASSWORD"` and passed straight to the tool, and is never written into results, snapshots' quoted text or files. Plans prefer non-secret test accounts for FE flows.

**C9 — Mutation-guard exemption** (`/qa:loop`). A state-changing BE scenario is dispatched without `--allow-mutations` only when every state-changing action in it is individually expected to be rejected: the first integer on its `**Expected:**` line is ≥ 400; every edge-case line has an expected status ≥ 400; its `**DB Check:**`, when present, is read-only (no `INSERT`, `UPDATE`, `DELETE`, `DROP`, `TRUNCATE`, `CREATE`, `UPSERT`); and no other bullet describes a write (`create`/`delete`/`update`/`insert`/`seed` steps). Any unclassifiable action (an edge case with no parseable status, a DB write, a write-ish step) keeps the scenario guarded. Residual risk, documented next to the guard: an unexpected 2xx on such a request lands a write once, which is the defect the scenario exists to expose — the test DB stays disposable. Every other state-changing scenario is marked `mutation-guard` as today.

**C10 — Harness scope.** A scenario step is executable only as a browser action (FE) or an HTTP request / DB query (BE) against an already-running app. Starting or building anything (`docker`, `make`, `npm`, migrations), editing files, or inspecting infrastructure is out of scope: the plan puts bring-up under `**Required services:**` as a human prerequisite and lists unobservable checks under `## Out of harness scope` (bullets with a one-clause harness reason; never `### FE-NN`/`### BE-NN` headings; a code defect is a Blocker, never out of scope). A tester that meets such a step returns `SKIP` for that scenario with reason `out of harness scope: <step>`.

**C11 — Tester dispatch contract.** Every tester dispatch (`/qa:run` Step 4; `/qa:loop` Steps 2.1, 2.1.8 retry, 3e, 4) sends a prompt with, in this order: `Plan: <plan_path>`; `Setup:` followed by the plan's `## Setup` section verbatim, or `Setup: none declared`; `Base URL: <resolved per C6>`; for the BE tester `DB connection: <the Required databases bullets (env var names / mcp__ names), or "none declared">`; the scenario blocks of that section (loop: with the mutation-guard marks); and the closing lines `Report NEED_INFO (kind + missing names) for missing prerequisites. Never print secret values.` Testers take env var names from the `Setup:` block and the `$NAME` tokens in the scenarios; they never look for values elsewhere.

**C12 — DB access rule (BE tester).** A DB check runs only through a connection the plan declares under `## Setup → Required databases`: an env var name is used with a CLI client (`psql "$DATABASE_URL" -tAc '<SQL>'`; `sqlite3 "$SQLITE_DB" '<SQL>'` where the declared name holds the file path; MySQL through the declared names `MYSQL_HOST`, `MYSQL_USER`, `MYSQL_DATABASE` plus `MYSQL_PWD`, which the `mysql` client reads from the environment so the password never appears on a command line: `mysql -h "$MYSQL_HOST" -u "$MYSQL_USER" "$MYSQL_DATABASE" -N -e '<SQL>'`), an `mcp__` name is used with that MCP server. A preconfigured MCP server that the plan does not declare is never used, whatever its availability: nothing establishes that it points at the test database. No literal host/user/password/path ever appears in a DB command. No declared connection → the `**DB check:**` field is `SKIP — no DB connection declared under ## Setup` and the API part still runs.

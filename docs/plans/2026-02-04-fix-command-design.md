# Design: `/fix` Command for Code Review Plugin

## Overview

The `/fix` command takes a single issue from a code review report (generated by `/review`) and performs a complete fix cycle: analysis, proposal, implementation, verification, and reporting.

## Input Format

The command accepts a copy-pasted issue block from the `/review` report:

```
/fix [SEVERITY] Title of Issue

**Location:** `path/to/file.py:42`
**Category:** Security | Performance | Architecture | Maintainability
**OWASP:** A05:2025 (optional)
**CWE:** CWE-89 (optional)
**Effort:** trivial | easy | medium | hard

**Problem:**
Description of the issue...

**Impact:**
Description of impact...

**Remediation:**
Suggested fix with code examples...
```

### Parsed Fields

| Field | Required | Description |
|-------|----------|-------------|
| `severity` | Yes | CRITICAL, HIGH, MEDIUM, or LOW |
| `location` | Yes | File path and line number |
| `category` | Yes | Security, Performance, Architecture, or Maintainability |
| `problem` | Yes | Description of what's wrong |
| `remediation` | Yes | Suggested fix (key input for implementation) |
| `cwe` | No | CWE identifier for vulnerability |
| `owasp` | No | OWASP Top 10 reference |
| `effort` | No | Estimated fix effort |

If the format is incomplete, the command prompts for required fields (minimum: location + problem).

## Workflow

```
/fix <issue block>
        │
        ▼
┌─────────────────┐
│  Parse Issue    │ → Extract: location, category, problem, remediation
└────────┬────────┘
         ▼
┌─────────────────┐
│ Analyze Context │ → Read file, imports, related code, patterns
└────────┬────────┘
         ▼
┌─────────────────┐
│ Propose Fix     │ → Present plan with code preview, wait for approval
└────────┬────────┘
         ▼
┌─────────────────┐
│ Implement Fix   │ → Apply changes using Edit tool
└────────┬────────┘
         ▼
┌─────────────────┐
│ Verify (smart)  │ → Select tools based on change type
└────────┬────────┘
         │
    ┌────┴────┐
    │ Failed? │──yes──▶ Auto-fix (max 3x) ──▶ loop back
    └────┬────┘
         │ no
         ▼
┌─────────────────┐
│ Generate Report │ → Status, changes, verification results
└─────────────────┘
```

## Phase 1: Analysis

After parsing the issue, analyze:

1. **Target file** at the specified location
2. **Surrounding context** - function/class containing the issue
3. **Related files** - imports, dependencies, existing tests
4. **Project patterns** - coding standards, similar code elsewhere

## Phase 2: Proposal

Present a concrete fix plan based on analysis and the Remediation suggestion:

```
## Proposed Fix for [SEVERITY] Issue Title

**Target:** `path/to/file.py:42-48`

**Approach:**
Brief explanation of the fix strategy, incorporating the original
Remediation suggestion and adapting it to the actual code context.

**Changes:**
1. In `function_name()`: description of change
2. Additional change if needed

**Code Preview:**
```python
# Current code (lines 42-48)
vulnerable_code_here()

# Proposed fix
safe_code_here()
```

**Verification Plan:**
- [ ] Tool 1 (reason)
- [ ] Tool 2 (reason)

Proceed with this fix? (yes/no)
```

**Wait for explicit user approval before making any changes.**

## Phase 3: Implementation

Upon approval:

- Use Edit tool for targeted changes (preserve surrounding code)
- Apply changes incrementally if multiple locations affected
- Keep changes minimal - only what's needed to fix the issue

## Phase 4: Verification

### Intelligent Tool Selection

Based on the change type, select appropriate verification tools:

| Change Type | Verification Tools |
|-------------|-------------------|
| SQL/Injection related | SAST (semgrep), relevant tests |
| Authentication/Auth | SAST, secret-scanning, integration tests |
| API endpoint | Linter, typecheck, API tests |
| Data validation | Unit tests, linter |
| Performance (queries) | Linter, relevant tests |
| Architecture/Refactor | Linter, typecheck, full test suite |
| Simple code quality | Linter only |

### Detection Heuristics

- CWE/OWASP present → always include SAST
- Change touches `password`, `token`, `secret` → secret-scanning
- Change in test file → run that test file
- Type annotations changed → typecheck

### Auto-iteration

If verification fails:

1. Analyze the failure (linter error, test failure, SAST finding)
2. Attempt automatic fix for the new issue
3. Re-run verification
4. Repeat up to 3 times total
5. Report final state

## Phase 5: Report

Generate a summary after verification completes:

```
## Fix Report: [SEVERITY] Issue Title

**Status:** ✅ Fixed | ⚠️ Partially Fixed | ❌ Failed

**Changes Made:**
- `path/to/file.py:42-48` - description of change

**Verification Results:**
| Tool | Result | Details |
|------|--------|---------|
| ruff | ✅ Pass | No issues |
| mypy | ✅ Pass | No type errors |
| pytest | ✅ Pass | 12 tests passed |
| semgrep | ✅ Pass | No findings |

**Iterations:** 1 of 3 (if applicable)

**Remaining Issues:** (if any)
- Issue that couldn't be auto-fixed

**Next Steps:**
- Run full test suite: `pytest`
- Commit when ready: `git add -p`
```

### Status Definitions

| Status | Meaning |
|--------|---------|
| **Fixed** | All verification passed |
| **Partially Fixed** | Main issue fixed but verification found new minor issues |
| **Failed** | Couldn't fix within 3 iterations |

**Changes remain uncommitted for user control.**

## Command Configuration

**File:** `plugins/code-review/commands/fix.md`

```yaml
---
allowed-tools: Bash(git:*), Bash(pytest:*), Bash(ruff:*), Bash(mypy:*), Bash(semgrep:*), Bash(npm test:*), Bash(eslint:*), Bash(tsc:*)
description: Apply fix for a single code review issue with verification and reporting.
model: claude-opus-4-5
argument-hint: <paste full issue block from /review report>
---
```

### Reused Skills

- `linter-integration` - for running project-specific linters
- `sast-analysis` - for security verification (when CWE/OWASP present)
- `secret-scanning` - for auth-related changes

The command runs verification inline (no subagents) since scope is a single issue.

### Error Handling

| Scenario | Behavior |
|----------|----------|
| Invalid issue format | Prompt for required fields |
| File not found | Report error, suggest checking path |
| No verification tools available | Skip verification, warn user |

## Key Design Decisions

1. **Input method:** Full issue block copy-paste (works across sessions)
2. **User approval:** Required before any implementation
3. **Verification:** Intelligent tool selection based on change type
4. **Auto-iteration:** Up to 3 attempts on verification failure
5. **Commit:** None (user controls when to commit)
6. **Model:** `claude-opus-4-5` for high-quality fixes
